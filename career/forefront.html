Forefront: memory and GPU optimization for standalone VR

Forefront is Triangle Factory's 32-player VR shooter, available on Meta Quest, Steam, PlayStation VR2 and Pico. Standalone headsets have very little RAM and GPU time to spare, so a lot of my work there was finding out where memory and GPU time were going and bringing them down. I joined in February 2026 as an intern and stayed on as a freelance developer.

The constraint

Shared memory and a mobile chip

A Quest 2 has 6 GB of RAM and a Quest 3 has 8 GB, shared by the OS, the CPU and the GPU. If a game uses too much, the OS simply closes it. On top of that, every frame is rendered for two eyes: at 72 Hz that leaves 13.9 ms per frame, at 90 Hz 11.1 ms.

A 32-player shooter with large maps has to fit inside both limits, so textures, fonts, distant scenery and draw calls all count.

01 · Memory

Duplicate fonts and textures

In Unity it's easy to end up with the same font or texture in memory more than once. TextMesh Pro needs some fonts in a Resources folder, while Addressables packs the same fonts into its own bundles, so they get loaded twice. With CJK localization and several font weights, that adds up fast on a headset with 6 to 8 GB shared by everything.

I tracked down where each duplicate came from and removed them, so the game keeps one copy of each asset instead of several. A batched UI material that copied six font atlases into a texture array now points at the atlases the fonts already own. In the Unity Memory Profiler, the total came out to 148 MB less RAM.

02 · Build pipeline

Keeping memory down after the fix

Memory fixes like this tend to come back the moment someone adds a new font. So I added a validation step that fails the build if a duplicate font reference survives, and prints the exact dependency chain so the offending prefab is obvious right away. It costs nothing at runtime and nobody has to remember the rule.

I also worked on custom build actions and memory stripping, so data the game doesn't need never ends up in the build or in RAM in the first place.

03 · Rendering

Far scenery: from CPU batching to GPU-driven drawing

Distant scenery used to be batched on the CPU. I moved that work to the GPU: a compute shader now does the batching and writes the draw arguments, and indirect draw calls consume them. The CPU no longer has to gather and submit that geometry itself every frame.
